# 2026-09-19 — 26.1 real runtime acceptance

## Build and environment

The tested JAR was `monkeycraft-1.4.2-26.1.jar`, SHA-256
`2a48ef6a643a5582dbff651ebe9fdba13bbe852853d71ba09045f1a2ef9dcbef`.
Minecraft 26.1 ran under Java `25.0.1` with session control enabled and a requested stream rate
of 20 FPS. This was a real PrismLauncher Minecraft session connected to `mp.imaginefun.net`;
it was not a phone test.

## Commands and observed results

The 26.1 Minecraft instance was already running and had already joined the server before the
browser runner connected to it. From `web/`, the runner invocation was equivalent to the
following; its password was read only in-process from the 26.1 instance configuration and is not
recorded here:

```sh
MONKEYCRAFT_CONFIG='<26.1 instance>/minecraft/config/monkeycraft.json' \
MONKEYCRAFT_REUSE_DEV=1 MONKEYCRAFT_LIVE_URL='<accepted game origin>' \
MONKEYCRAFT_LIVE_SOAK=1 MONKEYCRAFT_LIVE_MAX_FPS=1 DEBUG=pw:browser PATH=/opt/homebrew/bin:$PATH \
node tools/run-live-test.ts
```

`run-live-test.ts` connected Chromium/Playwright to that existing Minecraft session; it did not
launch Minecraft. The saved runner log reports two passing tests in 10.1 minutes: initial login
and video-frame rendering, followed by the ten-minute live soak and resize cycle. The diagnostic
artifacts are in `outputs/roadmap-2026-09-19-26.1-acceptance/`.

* The ten-minute stream ran for 600,028 ms. It decoded 6,273 frames, reported zero decoder
  errors, and ended at configuration counter 6 after four viewport-size changes.
  The final sample remained connected with `err 0`.
* The minimized interval began at 140,003 ms and ended at 280,015 ms. The native window was
  iconified during the interval; decoded frames grew from 1,485 to 2,888, for an observed
  average of 10.02057 FPS. `WindowMixin` intentionally returns `false` from `isIconified()`
  while a client is streaming, bypassing the vanilla iconified-window cap; the recorded native
  value `1`, reported value `false`, and 30 FPS limit are therefore the expected design result.
* HTTP `HEAD` and content checks passed for all 11 packaged web files: `index.html`, worker,
  manifest, favicon, four icons, CSS, JavaScript, and its source map. Each returned 200 and
  matched the expected byte hash.
* The input-release runner at
  `outputs/roadmap-2026-09-19-26.1-acceptance/input-release-probe.mjs` held Shift, then closed
  its browser without a key-up event. Server readback changed from `connected=true, shift=true`
  to `connected=false, shift=false`.
* The reconnect runner at
  `outputs/roadmap-2026-09-19-26.1-acceptance/reconnect-probe.mjs` first used Playwright
  offline emulation alone. That left the existing WebSocket connected, so it is explicitly not
  counted as a reconnect pass. The corrected run combined browser offline emulation with the
  server's `closeConnection(1006)`: it observed disconnected and Shift released, then restored
  connectivity, received more decoded frames, and kept Shift released.
* The embedded helper ran as a child process. Its observable state was `needsLogin` with no
  error and no listener. It generated a login URL and requested that the system open it; the user
  was asked to authorize that one node. Authorization completion and networked tailnet connectivity
  were not confirmed. No duplicate login request or identity replacement was performed.
* Normal Minecraft exit was confirmed. The helper process also exited; the config SHA-256 was
  identical before and after the session.

## Boundaries

The browser checks used a desktop Chromium/Playwright client and controlled WebSocket
interruption. They do not demonstrate physical mobile behavior, Wi-Fi/cellular switching,
authenticated embedded Tailscale connectivity, a tailnet peer connection, or a listener/forward
path. The minimized test establishes decoded-frame continuity while the designed streaming
override suppresses the vanilla iconified-window throttle.

The raw JSON, process samples, browser screenshots, and launch/live logs remain under
`outputs/roadmap-2026-09-19-26.1-acceptance/`.

## Inventory assertion correction and recheck

Screenshot review found that the old live test accepted any already-open Minecraft Screen as an
inventory screen. In 1.19 this was visibly the pause menu; the initial 26.1 inventory screenshot
also preceded visible inventory rendering. Those original screenshots do not establish inventory
identity. The original video and ten-minute results remain valid.

The test now closes an existing Screen, focuses the video area, always sends E, waits for a newly
opened Screen and at least four additional decoded frames, then captures the screenshot. The same
26.1 JAR was relaunched and rejoined ImagineFun. The strengthened run passed in 5.9 seconds
(one passed, unrequested ten-minute test skipped); visual inspection of
`26.1-inventory-recheck/live-inventory.png` confirmed the actual ImagineFun inventory slots.
Escape closed the Screen. The game then exited normally (PID 67605), and the final configuration
hash remained unchanged. See `26.1-inventory-recheck.log` and `final-config-check.json`.
