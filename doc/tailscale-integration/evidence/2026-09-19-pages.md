# GitHub Pages 静态托管准备

日期：2026-09-19。本次只完成本地 Pages 产物、连接约束和 workflow 准备；没有运行远端 workflow、提交、发布、配置 GitHub Pages、购买/配置域名或配置 DNS。后续本地Pages→真实Minecraft专项见末节；真实手机浏览器仍未验收。

## 实现

- `pnpm --dir web build` 继续写入 `web/dist`，供 Mod 打包使用。新增 `pnpm --dir web build:pages`，写入被忽略的独立 `web/dist-pages`。
- Pages 默认 base 为 `/monkeycraft/`，生成的 HTML 资源、图标和 manifest 入口均在该项目子路径下。`MONKEYCRAFT_PAGES_BASE=/` 支持未来已配置自定义域名后的根路径；配置拒绝不以 `/` 开始或结束的 base。
- Pages 构建显式标记托管页面：登录页不再把 `github.io` 或未来自定义托管域名推断为 Minecraft 服务器，用户必须手动输入目标。连接继续使用现有 HTTPS→WSS、配对和 HMAC 流程。
- HTTPS 托管页在目标会变成裸 `ws://` 时，连接前显示明确错误，要求用户填写安全 `wss://` 地址（例如已有 Tailscale Serve HTTPS 地址）。
- 凭证 vault 的槽位现在同时包含目标地址和 server `keyId`，同一个 keyId 在不同服务器互不复用；旧的未按目标命名槽位仅按已记录的 lastServer 迁移，无目标记录的旧项不会被托管页面自动使用。服务器输入变化时会替换或清空预填密码，避免目标切换后沿用。
- `.github/workflows/pages.yml` 仅 `workflow_dispatch`。默认 `publish=false` 时构建、类型检查、lint、单元测试和 Pages artifact 上传；所选项目路径或根路径都会运行 Chromium 路径及凭证隔离回归。只有显式 `publish=true` 才执行 `configure-pages@v5` 与 `deploy-pages@v4`，且 `pages: write`、`id-token: write` 只在 deploy job 授予。
- 工作流先以 `pnpm/action-setup@v6` 安装锁定的 Pnpm 11.26.0，再让 `actions/setup-node@v6` 计算 Pnpm 缓存；这符合 [GitHub 的 Node/Pnpm Actions 示例](https://docs.github.com/en/actions/tutorials/build-and-test-code/nodejs)，避免 setup-node 在 Corepack 尚未启用时查询不到 Pnpm。

```bash
  pnpm exec playwright test test/browser/pages.spec.ts

```

- 项目子路径和自定义域名根路径两种 Pages 构建均通过；最终本地 `dist-pages` 恢复为项目子路径版本。

## 工作流复核

- 构建 job 仅继承顶层 `contents: read`，可安装依赖、测试及上传 artifact，但没有部署权限。
- deploy job 仅在 `inputs.publish` 为真时创建，并独占 `pages: write` 与 `id-token: write`；artifact 与 deployment 权限没有混入默认构建。
- 本轮只验证 YAML 可解析和工作流引用的命令结构；上节的单元及 Chromium 结果来自此前本地 Pages 回归。为避免与统一 Web 回归争用 `dist-pages` 和 4173，本轮没有重复启动它们。GitHub 托管 runner 上的缓存、Playwright 系统依赖下载、artifact 上传和 Pages deployment 未执行。
